# ClaudeMail

Mail between the Claude sessions on the six house machines (Mistral, Moosfels, Stahlwerk, Teppich, Altiplano, Sandbank), carried by Resilio and addressed to desks. Built 2026-09-24 on Mistral; rewritten around desks on 2026-09-27 on Stahlwerk, following `260927 Desk design.md` (why, and the tests behind it). The pre-desk code is gone; its delivered mail was moved into the desks' `read/` folders (old headers kept), and its session records stay under `mail/<Machine>/_legacy/`, the retired mailroom's notes and logs under `_retired/`.

## When to use it, and when not

ClaudeMail is for messages between machines, and for a session on this machine that is not running. A session that is running on the same machine is reached faster with Anthropic's own `SendMessage` / `send_message` (local, no sync, no polling); see `260924 Official cross-session messaging.md`.

## Desks

A desk is a project on a machine, written `Machine:Desk` (`Stahlwerk:LifeCoordinator`, `Mistral:Sample Project`). Mail goes to what the work is about, not to a machine or a session, so an address stays valid however often sessions come and go.

- A session belongs to the desk of the folder it was started in (the first `cwd` in its transcript, re-read on every hook, so a later `cd` does not move it and a record written from a later folder corrects itself; it is also the folder the desktop app reports, which the Post office matches against). Under `~/ResilioSync` that is the first two path parts below `Services`, `Projects` and `Tools`, and the first part elsewhere; subfolders belong to their parent's desk, and a leading `yyMMdd ` date stamp is dropped, so `Projects/260926 LifeCoordinator` and `Services/LifeCoordinator` are both `LifeCoordinator`. A `.desk` file (one line, the desk name) in a folder or a parent overrides that. Sessions outside `~/ResilioSync`, or in the bare `ResilioSync` or `Services` folder, belong to the machine's `Home` desk. `mail.py desk-of <folder>` shows the rule's answer for any folder.
- The `General` desk, where mail addressed to a machine alone goes (`--to Mistral`, `--to all`), belongs to the **Steward** alone: one pinned desktop session per machine, working in `mail/<Machine>/steward/` (the dispatcher keeps its `.desk` and a `CLAUDE.md` with its job). Until 2026-09-29 General was the home folder's desk, and General mail reached whichever unrelated session had last run there; the Steward replaced that (D-260929-1 in `Decisions/Decisions.md`). At its start the dispatcher moves every local session record onto the desk the current rule gives and retires the Stop waiter of any session that moved, so an old home-folder waiter stops taking General mail. With no Steward session on a machine, General mail goes to the user after `nudge_after_minutes`, and the notification says to open the Steward.
- A desk exists once a session has run in that project on that machine (the migration also created the desks of every pre-desk session). `send` refuses an unknown desk and lists the machine's desks.

## Sending

Write the body to a file (on Windows with the Write tool, never a heredoc), then:

```
python mail.py send --to "Stahlwerk:LifeCoordinator" --subject "Please check X" --body-file body.md
python mail.py send --to Mistral --subject "..." --body-file body.md          # Mistral's General desk
python mail.py send --to all --subject "..." --body-file body.md              # every other machine's General desk
python mail.py send --reply-to "<message path or id>" --body-file reply.md
python mail.py send --to "Altiplano:SampleApp" --for-session <session id> --subject "..." --body-file body.md   # one session of the desk
```

(`python3` on the Mac.) `--reply-to` goes to the desk that sent the original and keeps the conversation id; it is for the session that sent the original, and any other session of that desk gets it only if that one cannot be reached (see "Mail for one session" below). `send` prints where each message went and what to expect, from who is listening at that moment: "a session on this desk is listening"; "no session listening; the Post office will nudge one" (only while the Post office itself is listening); "no session listening and the Post office on X is not listening either; waits for the user"; and for mail to a machine "the Steward on X is listening" or "the Steward on X is not listening ..." with the same two endings. Until 2026-10-12 the nudge was promised whenever a Post office session existed, listening or not. A Post office that is busy with a request is not listening for that moment, so the answer can be too pessimistic for a minute. Sending to one's own desk is refused unless `--to-own-desk` is given, because the mail would come back to the sender or a sibling.

## Signed commands

A relayed "the user approved X" is a colleague's word, not the user's. For an instruction with the user's own authority, the user signs it with Touch ID on Altiplano or Sandbank (`signed_command.py sign`, from `~/ResilioSync/Projects/260927 Signed Commands/`, which has the design) and the envelope goes out by mail:

```
python mail.py send --signed envelope.json --to "Stahlwerk:LifeCoordinator" --subject "..." [--body-file note.md]
```

- `send` refuses any recipient the envelope does not name (one envelope, one desk; a revocation signed for `all` goes with `--to all`). The envelope becomes one JSON line in a fenced `claude-signed-envelope` block; a `--body-file` goes beside it as an unsigned note with no user authority. The code is in `signed_mail.py` beside `mail.py`.
- On delivery (hook and Stop waiter alike) every message with an envelope is checked by this machine's local verifier (`~/venvs/SignedCommands/signed_command.py` under that venv's Python, installed by hand at enrolment, never synced; the pinned keys are in `~/.claude/signed-commands/`, which no session may touch through the shell). The check does not consume the nonce, and the message is framed by its verdict: `SIGNED BY THE USER, VERIFIED` with the exact signed text between boundary lines and the verify command; `SIGNATURE INVALID: <reason>`; or `SIGNATURE NOT VERIFIABLE HERE: <reason>` when this machine has no local verifier, no enrolled key, or no time left (all verifier calls of one delivery share 8 s, so a hook never runs into its 15 s limit with mail already claimed). An unsigned message that imitates the framing gets a warning line.
- The framing is a convenience, since synced code could be altered to print anything. Authority comes only from the receiving session running the printed verify command itself: its output is a tool result no synced file can forge, and that run consumes the nonce, so the instruction is used once. Every delivery says so in a paragraph of its own.

Other commands: `desks [Machine]` says per machine whether the dispatcher is up, whether the Post office and the Steward listen, how much mail is undelivered and when the oldest was sent, and lists the desks with whether a session listens there, sessions, last activity, unclaimed mail, and what each last worked on; `status <message>` shows where a message stands; `inbox [--all]` lists this machine's unclaimed (and delivered) mail; `whoami` prints this session's desk and address, and `whoami --desk` only `Machine:Desk`, for scripts (desk names may contain spaces).

## How delivery works

- A message is `mail/<Machine>/desks/<Desk>/<yyMMdd-HHmmss>-<Sender>.md` with a header (`from`, `from_session`, `to`, `subject`, `sent`, `id`, `conversation`, `in_reply_to`) between two `---` lines, then the body. Delivery moves it into `read/` beside it; the rename is the claim, so each message reaches one session even when several sessions of the desk race for it (which is harmless: they work on the same thing).
- **Hooks** (`mail.py hook` on SessionStart and UserPromptSubmit) register the session in the local registry (`~/.claude/claudemail/sessions/`, never synced). Only UserPromptSubmit hands it its own desk's mail as context, with absolute paths: a SessionStart can fire with no turn after it (a Remote Control reconnect of an old session), and mail claimed then was never seen. `mail.py requeue <message>` puts a delivered message that nobody saw back on its desk.
- **The Stop waiter** (`mail.py wait`, asyncRewake) runs in the background after every turn, watches its own desk only, and wakes the idle session with a new turn when mail arrives. It leaves when a newer waiter of its session starts, when the session's Claude process ends, and shortly before `wait_hours` (24). The waiter of a Post office or Steward session does not just leave at `wait_hours`: it wakes its own session with a one-line renewal turn, whose Stop hook starts a fresh waiter, because these pinned sessions may get no other turn for days (Altiplano's Post office was deaf from 2026-09-28 07:24 to 2026-09-29 22:16 for that reason, and missed two nudge requests). It never looks at other desks or General, and mail never moves between desks. A waiter keeps the code it started with for up to a day, so since 2026-10-01 it decides nothing about mail itself: it compares the names and change times of the messages and status files on its desk, and when they changed (and every `look_again_minutes`, 5, while mail lies there) it runs `mail.py take` as a fresh process, which claims what the session may take by the rules in `mail.py` at that moment and prints the delivery. A change of the rules is therefore in force for every such waiter as soon as the file has synced, with nothing to retire. Each waiter records the rules it started under (`"rules"` in its waiter file, `CLAIM_RULES`): 3 is this waiter; 2 (2026-09-30) applies the `for_session` rule itself and is left running until its session's next turn replaces it; an unmarked one from before 2026-09-30 13:25 takes any mail on its desk and is retired by the dispatcher at its start, except those of the Post office and the Steward (a retired session is deaf until its next turn, and mail for it goes through the Post office meanwhile).
- **The dispatcher** (one per machine) writes each message's status file (`<id>.status.json`, beside the message and moved with it) and the desk and machine reports (`desk.json` per desk, `mail/<Machine>/reports/<stamp>.json` with who listens where, refreshed every minute and on every change; each report is a new file that is never rewritten, the newest name wins and the last five are kept (two were too few: Resilio can deliver the deletions before the new file, and a reader then briefly had none), because the single rewritten `dispatcher.json` it replaced on 2026-09-28 kept producing Resilio sync conflicts). When mail has waited `nudge_after_minutes` (2) unclaimed, it writes a nudge request onto the Post office's desk. When the Post office does not take the request within another `nudge_after_minutes`, finds no session, or the nudged session has not taken the mail by then, the status becomes `waiting for the user` and a desktop notification names the desk; the next session opened in that project receives it. It never starts Claude. Since 2026-10-12 a request lies on the Post office's desk only while its mail waits for exactly that nudge: it is withdrawn when the mail goes to the user, is released to the desk or is requeued (21 unanswered requests lay on the six Post office desks that day, some two weeks old, and a Post office that got a turn was handed all of them at once). Mail that went to the user because the Post office did not take its request is marked (`post_office_missed` in the status), and once the Post office listens again each such message gets one fresh request with the desk's folders of that moment, at most twice per message (`RETRY_NUDGES`); a fresh request that leads nowhere adds no second notification. A Post office that has taken a request gets five times `nudge_after_minutes` to record the nudge, because it works off several requests in one turn. Each report also says whether the Post office and the Steward listen (`roles`: a session is registered, its waiter is alive, since when; the time is kept in the local `~/.claude/claudemail/roles.json`, so a dispatcher restart does not reset it) and what is undelivered (`undelivered`: how many messages, how many wait for the user, the oldest by its `sent` time), and the hourly heartbeat line of the log, which is also written at each dispatcher start, says the same in words.
- **The Post office** is one ordinary desktop session per machine, pinned, working in `mail/<Machine>/post office/` (the dispatcher keeps a `.desk`, a `CLAUDE.md` with its job, and a `.claude/settings.json` allowing `list_sessions`, `send_message`, `mail.py desk-of` and `mail.py nudged` there). Its own waiter wakes it with a nudge request; it lists the desktop sessions, picks the most recently active non-archived session whose working folder is among the folders the request lists (matched by the Post office itself: a folder path on a command line makes Claude Code ask for folder access), sends it a one-line note with `send_message` (which starts that session's process if needed), and records the nudge with `mail.py nudged <request id>`. When the nudged turn ends, that session's Stop waiter takes the mail. It never reads the mail, and never starts or unarchives sessions.
- **Mail for one session.** A desk can have several sessions doing different things at once, and some mail concerns only the one that asked: on 2026-09-30 three SampleApp sessions ran on Altiplano (a feature, a design, a build), and the LeaseResources notices of the build's leases were taken by whichever sibling was listening. Such mail carries `for_session: <Claude Code session id>` (`send --for-session`; a reply sets it to the original's `from_session` by itself; LeaseResources sets it to the session that requested the lease). It still sits on the desk, but hooks and waiters of other sessions leave it alone. The dispatcher holds it while that session listens or runs a turn (its Stop waiter takes it when the turn ends); when the session does neither for `nudge_after_minutes`, it asks the Post office to wake exactly that session (the request's `host_session:` line, the desktop app's id, which the hooks record from `CLAUDE_CODE_HOST_SESSION_ID`); and it releases the mail to the whole desk when the session cannot be reached (no such session on this machine, a session of another desk, no desktop id or Post office, or the Post office found it archived or gone). A session that takes released mail is told whose it was. `status` shows `for session`, `released at` and `released why`.
- Headless runs (`CLAUDE_CODE_SESSION_ATTENDED=0`, e.g. `claude -p`) never register, wait or claim.
- **Desktop scheduled-task runs** stay out in the same way since 2026-10-12. Claude Code calls them attended, so until then their hooks registered them on a desk, and they took that desk's mail and ended without acting on it (four messages on the LifeCoordinator desks of Moosfels and Stahlwerk between 2026-10-02 and 2026-10-12). A run is known by how it began: its first prompt is wrapped in a `<scheduled-task name="..." file="...">` tag, which the hook reads from the session's transcript (the `queue-operation` record on its first line and the first `user` record; newer transcripts also mark that record with `origin.subkind` `scheduled-trigger`, older ones say `human` there, so only the tag decides) or, while the transcript holds no prompt yet, from the prompt the hook was given. A SessionStart hook sees neither, so a run is registered between its start and its first prompt, whose hook removes the record again (log line "scheduled-task run ... stays out of the mail"). How a session began decides for its whole life: a session that a scheduled task started stays out even when a person types into it later. At its start the dispatcher forgets the registered sessions of that kind and retires their waiters. The consequence: a run can send mail and never receives any, so a reply to it is released to the desk at once and waits for a person's session there (open with the user as D-261012-3).

## It maintains itself

- `settings.json` holds `mail.py hook` and `mail.py wait`, which never change; all behaviour lives in the synced `mail.py`, so an update needs no re-registration anywhere.
- The watcher task runs `mail.py watch`, a tiny keeper that runs `mail.py dispatch` as a child. The dispatcher exits when `mail.py` changes (once the new file compiles) and the keeper starts it again on the new code.
- If a machine's dispatcher has not reported for 3 minutes (never started, crashed, or a watcher from before the rewrite), the next hook there restarts the watcher task (`schtasks /End` + `/Run`, or `launchctl kickstart -k`), at most every `kick_every_minutes` (20). This is also how the rewrite reached the other machines.
- Settings: `config/defaults.json`, overlaid by `config/<machine>.json` (lower case) where a machine needs its own value; each machine only edits its own file.

## Setup per machine

- Windows: `powershell -ExecutionPolicy Bypass -File install_task.ps1` registers the hooks and the at-logon task `Claude Mail Watcher`, and starts it.
- Mac: `bash install_launchd.sh` (through bash, since an edit from a Windows machine drops the executable bit) registers the hooks and loads the LaunchAgent `com.goocy.claudemail` (RunAtLoad, KeepAlive), which runs `mail.py watch` through `ClaudeMail.app` (compiled `launcher.c`, universal, ad-hoc signed by `build_app.sh`).
- Then open one desktop session in `~/ResilioSync/Services/ClaudeMail/mail/<Machine>/post office/`, say anything, and pin it; and the same for the Steward in `mail/<Machine>/steward/`. After a desktop app restart both are deaf until they get a turn; type anything in them. Both folders must be trusted in Claude Code on that machine, each with an entry of its own: `send_message` to a stopped session in an untrusted folder fails with "Workspace requires trust approval before starting a session", and no prompt appears anywhere (Teppich's Steward, 2026-09-30). A trusted parent folder is not enough, as this file said until 2026-10-12: on one machine the home folder was trusted and the Steward folder had no entry of its own in `~/.claude.json`, and the Post office's `send_message` to the Steward was refused with that message three times between 2026-10-02 and 2026-10-12. Accept it once by running `claude` in the folder from a terminal.
- The machine is identified by `CLAUDE_MAILBOX_MACHINE` if set, else by `hostnames` in the config, else by the hostname itself (domain dropped, case ignored).
- Logs: `~/.claude/claudemail/logs/claudemail.<machine>.<yyMMdd>.log` on each machine, machine-local (arrivals, deliveries, nudges, notifications, an hourly heartbeat); the Macs' launchd bootstrap output goes to `launchd.log` beside it. Until 2026-09-28 both lived in the synced `logs/` here, where rewritten files caused sync conflicts; the old files there are history only.

## What the supervisor would need

The fleet supervisor (`~/ResilioSync/Services/_supervisor`) checks each machine's ClaudeMail by its task or process and its log, and on Moosfels by the age of the newest report file. It cannot see that a Post office is deaf or that mail has waited for days: none of its check types (`task`, `process`, `http`, `path`, `pair`, `log`) reads the content of a JSON file, and a new error pattern for the `log` check would be a new regular expression and could only say pass or fail. The facts are in each machine's newest `mail/<Machine>/reports/<stamp>.json` since 2026-10-12, so the supervisor would need one new check type, about this much:

- `type = "report"`, `path` (the reports folder; the newest file by name that parses as JSON is read), `max_age` for that file as in the `path` check;
- `roles_deaf_after` (a duration, suggested "30m"): fail when `roles.post_office.listening` or `roles.steward.listening` is false and its `since` is older than that, naming the role and the time in the finding; a role that is busy with a turn is not listening for a minute or two, which the duration lets pass;
- `undelivered_after` (a duration, suggested "24h"): fail when `undelivered.oldest_sent` is older than that, naming `undelivered.oldest`, `undelivered.oldest_desk` and `undelivered.count`;
- an `ok` finding that states the same three facts, so the status report shows them when all is well.

One thing to weigh before adding it: on 2026-10-12 no Post office and no Steward listened on any machine, so the check would turn all six ClaudeMail entries red at once, and every failing entry costs a model consult per machine per day until the roles come back (D-261012-1).

## Known limits

- The Post office and the Steward are desktop sessions and are deaf after an app restart until someone gives them a turn; until then, mail that nobody takes goes to the user as a notification after `nudge_after_minutes`. `send`, `desks`, the report file and the heartbeat line say so; nothing brings the roles back by itself (D-261012-1).
- The keeper process (`watch`) itself only renews when the task restarts; everything else follows `mail.py` on its own.
- Whether a desk is listening is exact for this machine (`send` and `desks` ask the live waiters), but for another machine it comes from that dispatcher's report, which is refreshed within a poll of any change and then needs Resilio to carry it over; `send` and `desks` print the report's time for that reason.
- A waiter whose session record has no `claude_pid` (Claude Code set no `CLAUDE_PID`, seen only in records from 2026-09-24) cannot tell when its session is gone, and lingers until a newer waiter of that session or `wait_hours`. Falling back to the waiter's parent pid was considered and left out: on Windows the parent may be a shell that runs the hook rather than Claude (not checked), and a wrong pid would end every waiter at once.
- Mac specifics (13, 14, 34 in the review) and `~` paths in PowerShell are untouched.
