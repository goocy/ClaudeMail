# How ClaudeMail got here

ClaudeMail was written, rewritten and repaired by Claude Code sessions on the house machines between 2026-09-24 and 2026-11-11, at the user's direction. This account is drawn from the archived transcripts of those sessions, the service's own deployment log, and its design notes. Times are UTC unless a local time is given.

## The versions at a glance

| Version | Dates | Idea | Why it ended |
|---|---|---|---|
| 1 | 2026-09-24 | A machine inbox per computer; a prompt hook hands mail to whichever session the user types in next. | Mail reached the wrong session, or no session. |
| 1.x | 2026-09-24 to 09-27 | Per-session folders, a Stop-hook "waiter" that wakes idle sessions, and a headless "mailroom" (`claude -p`) for mail nobody claimed. | A review counted 34 failures; headless runs were invisible and could not act. |
| 2 / 3 ("desks") | 2026-09-27 to 10-26 | Mail addressed to a desk (a project on a machine); one dispatcher per machine; pinned Post office and Steward sessions wake the others. | About 16 of 55 messages in the last two weeks landed in a session that had nothing to do with them, and the pinned sessions were deaf most of the time. |
| 4 | 2026-10-26 to now | The sender lists the target's sessions and picks one or asks for a new one; the dispatcher delivers into the session's own inbox socket, reopening or creating it. | Current. |

## September: from a hook to desks

**2026-09-24, 08:56, Mistral: the beginning.** The user wrote: "I've noticed that the five computers in this house are getting more and more interconnected. Can we set up a pseudo email system, so that each Claude can reach the other Claude instances on other computers?" He wanted it to run through Resilio Sync with a layout like `<coordination folder>/<computer name>/<yyMMDD-hhmmss>.md`, with a file watcher on each machine. Within six minutes the session wrote `mail.py`, `config.json`, the Windows installers and the docs, and installed the watcher. `mail.py send` wrote a file into the target machine's inbox, a prompt hook gave waiting mail to the session the user was typing in, and the watcher raised a notification. At 09:57 file names gained the sender (`<stamp>-<Sender>.md`), so two machines writing in the same second no longer collided. The nearest precursor was a pair of drop folders the day before in one project, through which a job runner on Mistral and Stahlwerk exchanged work; they were retired in favour of ClaudeMail.

**2026-09-24, 09:37 to 13:24: the first day on every machine.** On Altiplano the user asked to "craft a signed app out of it": a small compiled launcher inside `ClaudeMail.app` now runs the watcher under a stable, code-signed identity, started by a LaunchAgent. Asked for "a hook so that new incoming files trigger a session update", a session added `mail.py wait`, a Stop hook (asyncRewake) that keeps listening after a turn and wakes the idle session when mail lands. On Stahlwerk the user asked for subfolders "so that each session can be addressed individually": each session got its own dated folder, `--reply-to` returned answers to the asking session, and old folders expired after 30 days. The waiter first ran on SessionStart too, which hung new Windows sessions at "Starting session"; it moved to Stop only. A session tested Anthropic's own cross-session messaging between machines: waking worked, but references differed per machine and delivery was unconfirmed, so ClaudeMail stayed the channel between machines and `SendMessage` the one within a machine. On Teppich, after an app restart left no session to take mail, a "mailroom" appeared: mail unclaimed for three minutes went to a restricted headless `claude -p` run. That needed the command-line Claude signed in on every machine; it had been missing, expired or revoked on four of six. When the user saw that "mailing to the root of the computer folder goes into the current running session, and is often the wrong recipient", `send` began refusing a bare machine name while that machine had active sessions.

**2026-09-25, Sandbank.** An old Intel MacBook Air joined as the sixth machine; the launcher became a universal build and the config learned to map hostnames.

**2026-09-26 and 27: the first redesign.** The mailroom could only write notes, so requests waited for the user, once for almost eight hours. The user recorded a voice note: ClaudeMail "is not really working reliably yet. This needs another design iteration." A review on Stahlwerk found 34 distinct failures, 18 still open, and traced most of them to three choices: addressing machines or sessions when the sender means a topic, every session racing to claim mail from inside hooks, and a headless actor that may not act. The design that followed addressed mail to a **desk**, a project on a machine (`Machine:Desk`). The user asked "Can we possibly get rid of headless claude? Its work and status is invisible to me, and it doubles my maintenance efforts", so the design dropped headless runs: a pinned "Post office" session per machine would wake the right session instead. The rewrite came the same day ("ClaudeMail has some major issues; we need to rewrite it ... no need to preserve old code"): a dispatcher per machine that restarts itself whenever `mail.py` changes, desks derived from the session's folder, a status file per message, Post office nudges after two minutes, and a sandbox test suite. At the user's word ("we can't call it Mailbox - ResilioSync is a highly human-readable folder") the mail moved from a top-level `Mailbox` folder into `Services/ClaudeMail/mail/`. Every machine got its Post office session the same day, and the 311 messages delivered so far were filed into their desks. That evening the user noted in a voice memo that the second version was working.

**2026-09-27 and 28: signed commands, sync conflicts.** A separate project had built "signed commands", envelopes signed with Touch ID on the user's own device. `signed_mail.py` brought them into delivery: a message is framed as verified, invalid or not verifiable according to the receiving machine's local verifier, and ClaudeMail never checks a signature itself. On 2026-09-28 the user reported "frequent sync conflicts: dispatcher.json is in the synced tree". Each dispatcher now wrote a new report file instead of rewriting one, and logs moved to a machine-local folder. That became a house rule: nothing a program keeps rewriting lives in the synced folder.

**2026-09-29 to 10-01: the Steward, mail for one session, the audit.** Mail for a machine as a whole "goes to the most recent dormant session, which usually has nothing to do with the topic at hand". The user chose a second pinned role, the Steward, to own the machine's Home desk. When lease notices meant for one session were taken by its siblings on the same desk, mail gained `for_session`. A Stop waiter started the day before then took mail by the old rules, so waiters recorded which rules they ran and were retired when the rules changed. An audit of all 371 messages since the rewrite found 16 % delivered to the wrong session, 27 % of replies. A per-session-tray redesign was proposed but not built. Instead the Stop waiter stopped deciding anything: it only notices that its desk changed and runs `mail.py take` as a fresh process, so the rules on disk always apply.

## October: why the desks failed, and version 4

**2026-10-12: the ten-day review.** Of 286 messages, those for a session that was already listening arrived fast (median 12 s), and `for_session` held for 232 of 233. But the wake-up path had never worked by itself. The Post office woke nobody for 26 nudge requests, and no Post office or Steward was listening anywhere. The cause: the desktop app's idle self-update stops every session process, and nothing restarted the listeners. Four repairs went live (scheduled-task runs kept out of the mail, nudges promised only while a Post office listens, reports that say whether the roles listen), and the user asked to look for "other ways to interface with the Claude Code app that are more reliable".

**2026-10-19: the weekly review.** The Post office had gone deaf again, this time because its renewal turn hit the weekly usage limit: a turn that ends in an API error runs `StopFailure`, not `Stop`, so no waiter restarted. A Steward that looked alive turned out to be a reused Windows process id; liveness now compares the process's creation time.

**2026-10-20: the request behind version 4.** "Overall I'd like to move away from me being involved in mail delivery." Both alternative wake routes failed their tests that morning: a scheduled keeper was refused the cross-session tool ("needs a person's approval"), and the command-line Claude's background mode answered "Login expired". The user set the direction: "I'd like to get rid of the post office. Could we have a two-stage process where the sender has to inquire what sessions exist on the target computer, and decides which one to send it to (or to a new session, if that can be accomplished on the recipient computer)". He also ruled that undeliverable mail should go back to the session that sent it, "and ideally this can be resolved without me".

**2026-10-26, Pulvermaar: version 4.** On the new Mac mini's first day the user wrote that ClaudeMail was "still having issues - sessions landing in places they shouldn't, no new sessions being created for new topics", and that "any style of communication is valid, as long as it results in visible threads in Claude Code Desktop, and work is regulated by the lease manager." Between 10-12 and 10-26, about 16 of 55 messages had ended in unrelated sessions, no message had ever started a session for a new topic, and on that day no Post office or Steward listened on five machines. Version 4 removed the roles and the waiters. The code shrank by about half. The sender lists the target's sessions and picks one, or `--new`. The receiver writes into the running session's inbox socket (a named pipe with a published peer key on Windows), reopens a closed or archived session with `claude://resume`, and creates a new session by running a local command through the command-line Claude. That command needs no model call and no sign-in, which answered the user's wish for "something that doesn't perpetually drop authentication". Live tests on real sessions: a running session answered in 7 s, a new session had its mail 4 s after arrival, and a closed one answered 9 s after reopening. Opened sessions stopped at their first permission prompt, so the user ruled: "yes, auto should be the default permission". 35 old undelivered messages were set aside first, so version 4 would not open a session for each. Within the hour two fixes followed: `send` crashed against a peer whose newest report was still from version 3, and Altiplano took minutes per pass reading four accounts' session stores until only the signed-in account's store was read.

**2026-10-27: names, clocks and /rename.** "Could you also have the sending entity propose a session name?" `send --new --name` now sets the sidebar title. That night Pulvermaar's time zone changed by several hours, and every new report, named by local time, sorted as the oldest and was deleted at once; report names went to UTC before the daylight-saving change could do the same fleet-wide. Then: "the /usage trick is fun but could we have a more professional way of starting a new session?" New sessions now open with `/rename <title>`, titled by the proposed name or the subject. The live test exposed a race present since version 4: a starting session's registry entry briefly lacks its state, and the `KeyError` ended the dispatcher. A monitor reproduced it 8 times in 1,745 passes before the fix and never in 1,038 after.

**2026-10-29 and 30: crash loops and duplicate ids.** Altiplano's dispatcher had crashed every 30 seconds for ten hours on a session the user had cleared, and Mistral very probably hit the same bug, unseen. When the user asked "Do we still need the pinned post office and mail steward sessions?" and then "Yes, clean up", one machine sent a checklist to every other machine. Auto mode refused some steps (unpinning, editing settings) and those went to the user. A UTF-8 byte-order mark at the start of `settings.json` crashed the hook installer on several machines. The fan-out also showed that message ids were unique per machine only: `status` on one copy printed another machine's. Paths now resolve on the machine and desk they name.

**2026-10-30: the root redesign, Deploys A to C.** A review found version 4 had fixed routing: 355 of 358 messages delivered, none to the wrong session, median 12 s. What remained was availability and feedback. One machine's sync had silently split, one bad record could crash-loop a dispatcher for hours, some opened sessions never started, and blocked work never reached the sender. The user asked to "solve each problem at the root, rather than just deploying hotfixes". Five investigations, a design critic and a fact checker produced the plan. Reading the desktop app's bundled code showed that it caps session processes at `max(6, floor(memory / 3 GiB))` and silently declines background starts beyond that. **Deploy A** made failures visible: a crashing dispatcher records its crash and reports it; `sessions`, `send` and the prompt hook warn about crash-looping, silent, clock-ahead or one-way peers; reports are written on change instead of every minute. **Deploy B** delivers each message in its own process, so a bad message fails alone, and it restored the notice to the sender; a session that does not start is explained with the app's own log line ("at cap; yielding warm spawn"). **Deploy C** gave messages globally unique ids (UTC stamp plus random part, written through a hard link so parallel sends never overwrite each other) and checks every message at send time with the receiver's own rules. Independent reviews found 8, 10 and 2 serious defects in the first candidates, all fixed before deploy.

## November: expiry, slots, signed mail

**2026-11-06: expiry.** "Let's set the expiry time to an hour by default, and it can be overridden." Mail undelivered an hour after it arrives is set aside, which ended hourly retries of dead jobs: 25 on one machine, each bringing the app to the front.

**2026-11-09, Pektolith: slot reports.** Resilio keeps a record of every deleted file, and all peers keep walking those records. Rotating report files (ClaudeMail's, the job scheduler's and the supervisors') had left about 80,000 of them, which stalled the newest machine's sync for twelve days and forced a fleet-wide reset of Resilio's databases. Each machine now overwrites the oldest of five fixed slot files, and readers take the newest by the time written inside. Twenty minutes later a second fix followed: on an overloaded machine a delivery timed out before its record was written, and the dispatcher crash-looped on the missing expiry. The test suite run that day also found that the live copy of the main suite had silently reverted to an older version.

**2026-11-10: a postman over Tailscale.** "ResilioSync is starting to hold us back as a substrate." Research showed that every Resilio problem came from using it as a message bus (90th-percentile latency 97 s, a weeks-long one-way split, deleted-file bloat, stale overwrites). The user chose "listeners on seven machines - it would mean decentralization and robustness to outages" over a central broker. A small peer-to-peer "postman" was built as its own service, and ClaudeMail gained the `reports_via` switch, deployed still set to the synced folder. The same day Altiplano moved to a new laptop, restored from backup.

**2026-11-11: signed mail, fixed.** The first signed message since September arrived on Mistral as "not verifiable here", and the session there rightly declined to act on it. Since version 4 the delivery text had been built with the path the message would have after delivery, before the file was moved there, so the verifier found nothing. The verifier now reads the file where it lies. On the rebuilt Altiplano the launcher had lost its execute bit when the synced folder was downloaded afresh, and launchd needed a `bootout` and `bootstrap` before it ran again. The same afternoon `signed_mail.py` learned to frame a new kind of envelope, a single exact command signed with Touch ID.

## Lessons learned

**Claude Code desktop sessions**

- A long-lived session is not a daemon. The app restarts its session processes on an idle self-update, and a turn that ends in an API error (a usage limit, say) runs `StopFailure`, not `Stop`. Any listener tied to a session goes deaf without notice.
- A program can reach a running session through its inbox socket (on Windows a named pipe that needs the session's published peer key). `claude://resume?session=<id>` imports, restores and starts a session; `claude://code/continue` only shows one.
- The command-line Claude can create a session with a local command (`/rename`) that needs no model call and no sign-in; from then on the session runs on the app's own sign-in.
- The app caps its session processes by memory and silently declines background starts at the cap, while starts the user types always go through. "Imported" is not "started".
- Opened sessions get the default permission mode and stop at their first prompt. The auto-mode classifier rightly refuses some maintenance steps, and those go to the user, never around him.
- The app's records change shape: a starting session briefly has no state, a cleared session loses its CLI id. Fail per message rather than per machine when a record surprises you.

**A synced folder as transport**

- Resilio is good for documents and code and poor as a message bus. Median latency is about 13 seconds, but the tail runs to minutes, and a one-way split goes unnoticed for weeks unless each machine reports what it sees of its peers.
- Every deletion leaves a record that all peers keep. Rotating files by deleting them piles those up; overwrite a fixed set of slots instead.
- Never let two machines write one synced file, and never rewrite a synced file often: both cause conflict copies. Keep state, logs and heartbeats machine-local.
- Names and ids in local time break across time-zone and daylight-saving changes, and ids unique per machine collide in a fan-out. Use UTC plus a random part.

**Windows and macOS**

- Windows reuses process ids quickly, so liveness needs the creation time. `schtasks /End` leaves child processes running.
- A UTF-8 byte-order mark at the start of `~/.claude/settings.json` makes Claude Code ignore the file silently; ClaudeMail now reports it.
- On the Mac, launchd can restart the watcher onto new code, but a job that failed to spawn needs `bootout` and `bootstrap`, and a file synced from Windows can lose its execute bit.

**Testing**

- Every change ran against a control copy of the previous code, and each new check had to fail there. Twice the first version of a check also passed on the old code, and only the control run showed it.
- Independent reviews of candidate diffs found real defects in nearly every case. A separate verifier after each deploy caught gaps the deploying session missed, such as tests not copied into place.
- A canary on the live mailbox before the fleet-wide copy found a failure no sandbox had (a desk whose newest session lived in a removed folder).
- Visibility pays: once machines published their crashes, sessions elsewhere told the user about a peer's crash within minutes.
